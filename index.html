DAY 01

What is LangChain?

LangChain provides reusable building blocks for working with language models. Instead of manually writing the complete prompt and handling raw text every time, LangChain lets us connect components such as prompt templates, LLMs, and output parsers into reusable workflows.

Prompt Template

A reusable prompt containing variables that can be filled with different values.

Chain

A repeatable sequence where components such as a prompt, LLM, and output are connected together.

LCEL

LangChain Expression Language, used to connect components using the pipe operator.

DAY 02

Prompt Templates & Output Parsers

A prompt template lets us write a prompt once and reuse it with different values. Instead of rewriting the entire prompt, we can use placeholders such as {product_name}.

PROMPT TEMPLATE
Explain {product_name} in simple words.
product_name = LangChain

PromptTemplate

Creates reusable prompts with variables that can be replaced with different values.

Output Parser

Helps handle the output returned by an LLM in a predictable format instead of relying only on free-flowing text.

Structured Output

Structured responses, such as JSON, make it easier for software to read specific fields from an LLM response.

STRUCTURED OUTPUT EXAMPLE
{
    "name": "LangChain",
    "type": "Framework",
    "purpose": "LLM applications"
}
DAY 03

Memory & Tool Calling

An LLM call is independent by default. Memory allows an application to keep track of previous conversation messages and provide relevant history to the model during the next interaction.

Conversation Memory

Keeps track of previous messages so an LLM application can use earlier parts of the conversation.

Chat History

Stores previous user and assistant messages that can be provided to the model in later interactions.

Tool Calling

Allows an LLM to choose and call external functions such as calculators, search tools, or database lookups.

User
→
LLM
→
Tool
→
Result
TOOL-CALLING EXAMPLE

User asks: What is 9283 × 742?

Instead of guessing the calculation, the LLM can decide to call a calculator tool and use its result to produce the final response.

Tool Schema

Defines what a tool does and what information it expects when it is called.

Function Calling

The model can determine when a function or tool should be used and what arguments should be passed to it.

DAY 04

What is LangGraph?

LangGraph is designed for decision-making systems where the next step may depend on what happened previously. Unlike a simple fixed chain, a graph can contain different paths, decisions, and updates to shared state.

CHAIN

Fixed Sequence

Step A → Step B → Step C

A chain normally follows a predefined sequence of steps.

AGENT

Decision Making

Task → Agent

An agent can decide what action or path should happen next.

Core LangGraph Concepts

01

Node

A node represents one step or operation in a graph.

02

Edge

An edge connects nodes and describes what happens next.

03

Conditional Edge

A conditional edge creates a decision point where the next path depends on the result of a previous step.

04

State

State is the information passed through the graph and updated as the process moves from one step to another.

GRAPH THINKING

A simple decision process can be represented as:

DAY 05

Orchestrator Agents

An orchestrator agent receives a task, understands what needs to happen, and routes the task to the right specialized agent or agents. It acts more like a manager than a worker.

User Task
↓
Orchestrator / Supervisor
↙ ↓ ↘
AGENT 01

Research Agent

Handles research-related tasks.

AGENT 02

Analysis Agent

Handles analysis-related tasks.

AGENT 03

Report Agent

Handles report or response generation.

01

Router Pattern

The orchestrator determines where a task should be sent based on what needs to be done.

02

Multi-Agent System

Multiple specialized agents can work on different parts of a larger task.

03

Shared State

Agents can work with shared information that moves through the overall workflow.

04

Supervisor Agent

A supervisor can coordinate specialized agents and decide where work should go next.

WHY OUR PROJECT NEEDS AN ORCHESTRATOR

Our upcoming project uses an orchestrator pattern because the system needs to receive raw data and decide which specialized agent should handle the next step.

The orchestrator does not perform every task itself. Instead, it coordinates the agents responsible for different types of work.
